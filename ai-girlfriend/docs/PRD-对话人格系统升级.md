## 原始需求复述

在「小暖」已上线的 AI 恋人 PWA 上做一轮**对话质量升级**，主攻四个方向：**对话连贯性、人格一致性、用户情绪感知、剧情与关系成长**。引擎路线保持云端 + 本地双轨，**重点强化本地规则层**，保证没网 / 没 API Key 时体验不掉档。所有已上线能力零回归。

---

## 一、产品目标

### 一句话目标

> 把小暖从**「一句话一次正则匹配、从固定池里抽一条」的应答机器人**，升级为**「记得住我们在聊什么、认得出我此刻什么情绪、无论切哪张人格卡都始终是同一个人、并且在和我共同积累经历」的恋人** —— 且这一切在**断网、无 API Key** 的纯本地规则层同样成立。

### 三个正交目标

| # | 目标 | 从什么样 → 变成什么样 |
|---|---|---|
| **G1 连贯** | 本地规则层具备多轮话题追踪与追问链 | 从「聊三句就断片、抛回『然后呢』」→「在一条话题线里持续推进，接得住上一句」 |
| **G2 一致** | 人格卡下沉到规则引擎，拥有独立口癖与行为倾向 | 从「切成傲娇卡，规则回复还是软萌」→「断网状态下也能一耳朵听出是哪张卡」 |
| **G3 共情与成长** | 感知用户情绪并针对性反应；主动消息由剧情驱动 | 从「同一个词不分喜怒回同一句、主动消息随机抽签」→「难过时她先共情，且你们有在推进的共同经历」 |

## 二、现状事实核验（写 PRD 前实际读码验证）

> 以下为逐行读取 `engine.js`（1156 行）、`app.js` 关键路径、`openclaw.js`、`bridge/xiaonuan-bridge.js` 后**实测确认**的事实，不是推测。它们是本轮需求的直接依据，请工程师按此定位改造点。

### 2.1 `memory.lastTopic` 是一个死字段 —— 话题状态机根本不存在

`engine.js:707` 读取了 `memory.lastTopic`：

```js
const topic = text.trim().length > 4 ? text.trim().slice(0, 12) : (memory.lastTopic || "那件事");
```

但**全仓库（`engine.js` / `app.js` / `openclaw.js` / `bridge/xiaonuan-bridge.js`）没有任何一处对 `lastTopic` 赋值**。这意味着该表达式**永远**退化为「当前这句话的前 12 字」，或在短句时退化为字符串「那件事」。

> **结论**：小暖不是"话题记得不牢"，而是**从来没有过话题记忆**。这是 G1 最有力的论据，也是 P0 需求 A2 的直接来源。

### 2.2 Lv.1 时多个意图池只剩 1 条回复 —— 复读是必然而非概率

回复池 `R` 的每个条目带 `lv` 门槛，`reply()` 按当前好感等级过滤后再抽取。实测过滤结果：**Lv.1（初识）时 `night` / `noon` / `morning` / `sleepy` / `weather` / `age_ask` / `time_ask` 等意图的可选池各仅剩 1 条**。

同时防复读机制只比对单条 `state.lastReply`：

```js
while (chosen.t === lastReply && pool.length > 1 && guard < 8) { chosen = pick(pool); guard++; }
```

—— 只防**相邻重复**，且 `pool.length > 1` 不满足时直接放弃。新用户（好感度最低、最需要留存的阶段）**每天晚上都会收到一模一样的晚安**。

> **结论**：扩池 + 跨轮去重必须是 P0。这是新用户流失最刺眼的体感缺口。

### 2.3 人格卡对规则引擎的影响只有一处，且极其微弱

`PERSONA_CARDS` 三张卡（`xiaonuan` 软萌 / `xiaonuan_tsundere` 傲娇 / `xiaonuan_clingy` 粘人）目前**只作用于云端 `systemPrompt`**。在 `Engine.reply()` 内部，`persona.tone` 的唯一用途是挑选 `suffixPool`（即 `MOODS[2].suffix` 或 `MOODS[3].suffix`，各 3 条心情后缀）。

**回复池 `R` 三张卡完全共用**；`genderSwap` 只做性别名词替换，不涉及性格话术。

> **结论**：断网时切人格卡 ≈ 无效操作。这是 G2 的直接来源。

### 2.4 `question` 兜底正则捞网过宽，实质输入被打成敷衍

`detect()` 是**顺序线性匹配、首个命中即返回**。`INTENTS` 共 **30 条**，末位兜底项 `question` 的正则包含 `吗|呢|什么|怎么` 等高频虚词，会把大量本应进入具体意图的句子提前截走；再往后就是 `chat` 兜底，回「原来是这样呀！然后呢」。

> **结论**：意图识别需从「顺序硬匹配」升级为「关键词加权打分 + 置信度」，否则话题状态机拿不到可靠原料。

### 2.5 V-A 情绪模型建模的是小暖自己，用户情绪完全未被感知

`Emotion.apply(state.emotion, intent, delta)` 的输入只有**意图**与**好感度增量**，不含任何用户情绪信号。因此「升职了累死我了哈哈哈」与「撑不住了真的好累」都命中 `tired`，施加**完全相同**的情绪冲量，输出**完全相同**的回复。

> **约束提醒**：V-A 是小暖的核心壁垒，本轮**只在 `apply` 前加一层调制，不改其数学模型**。

### 2.6 主动消息是无因果的随机池

`PROACTIVE.random` 为固定文案池，由 90 秒轮询 + `Math.random() < 0.35` 触发。同一句「我刚刚看到一只超可爱的猫」会在几天内重复出现，且**永远没有后续** —— 没有剧情线、没有共同经历，好感度只是一个数字。

### 2.7 ⚠️ `Engine.reply` 有 4 个调用点，签名必须向后兼容

这是本轮**最容易踩的回归雷区**。`Engine.reply(text, state)` 当前有四个互相独立的调用方：

| # | 调用点 | 场景 | 备注 |
|---|---|---|---|
| 1 | `app.js:889` | 网页聊天主链路 | 传入 `dating`、`lastReply` |
| 2 | `app.js:1642` | **语音通话** `callThink` | **未传 `dating`**，字段集与 #1 不同 |
| 3 | `bridge/xiaonuan-bridge.js:208` | OpenClaw 本地桥（Node） | 独立 state 结构 |
| 4 | `openclaw.js:133` | 服务端 OpenClaw 供应商 | 独立 state 结构 |

> **硬性要求**：
> - **`Engine.reply` 的函数签名不得变更**（仍为 `reply(text, state)`）。
> - **所有新状态只能以可选字段挂在 `state` 上**，且在引擎内部必须有默认值兜底（`state.topic || null` 这类写法）。
> - 任一调用方**不传新字段时，必须仍能正常返回回复**，不得抛错、不得降级为空。
> - 新增的引擎能力若需要写回状态，**返回值中带出**（如 `r.topic`），由各调用方自行决定是否持久化，**引擎内不得直接改写传入对象以外的全局状态**。

### 2.8 工程约束现状

- `package.json` **无任何 `dependencies`**，`engine.js` 是零浏览器依赖的纯函数模块（可在 Node `vm` 中加载）。本轮**不得引入任何 npm 包、构建工具或框架**。
- 仓库内**无持久化测试文件**（历史文档提到的 19/19 为一次性脚本）。本轮建议补一个零依赖的 `test/engine.test.js`（纯 Node 运行）。
- `load()` 采用 `Object.assign(defaultState(), JSON.parse(raw))` + 逐字段兜底的模式。**所有新增 state 字段必须同时在 `defaultState()` 声明并在 `load()` 中补兜底**，否则老存档（含云端加密存档）读取即崩。

## 三、用户故事

> 每条故事都配「改造前 vs 改造后」对话示例。**示例即验收手感**，工程师请以对话效果为准，不要只看功能描述。
> 除特别标注外，所有示例均为**断网 / 无 API Key 的纯本地规则层**表现。

### 方向一 · 对话连贯性

#### US-A1 我希望她记得我们正在聊什么，以便我不用每句话都重新交代背景

**作为**一个下班后想吐槽的用户，**我希望**小暖在连续几轮里都停在同一个话题上，**以便**我不用每说一句都从头解释。

> **改造前**（`memory.lastTopic` 无写入点，每轮都是独立匹配）
>
> 我：今天加班到十一点
> 小暖：辛苦啦！累了就歇一会儿，喝口水伸个懒腰~
> 我：老板又临时加需求
> 小暖：原来是这样呀！然后呢然后呢？　← 抱怨后面接「然后呢」，敷衍感拉满
> 我：我真的服了
> 小暖：怎么啦？跟我说说嘛，我在听呢 🥰　← 回到起点，像第一次听说

> **改造后**（话题 `work_overtime` 建立，`turns` 累加，槽位记住「十一点」「老板」）
>
> 我：今天加班到十一点
> 小暖：十一点……你又是最后一个走的吧 😤 饭吃了没？
> 我：老板又临时加需求
> 小暖：又是他！这周第几次了……需求是当天提当天要吗？
> 我：我真的服了
> 小暖：我也服了。你先别管他了——现在到家没？

#### US-A2 我希望她问出口的问题能接住我的回答，以便我觉得她真的在听

**作为**一个愿意回答她问题的用户，**我希望**小暖在我回答后给出针对性反馈，**以便**我不会觉得她只是在走流程。

> **改造前**（追问是随机抽的，与上一轮无关联）
>
> 小暖：那你现在感觉怎么样？有没有好一点？
> 我：好多了
> 小暖：具体讲讲？我想知道细节~　← 她自己问的，却没接住答案

> **改造后**（追问链推进到下一级，且引用上一轮结论）
>
> 小暖：那你现在感觉怎么样？有没有好一点？
> 我：好多了
> 小暖：那就好……我刚还担心你 🥺 那答应我今晚十二点前睡，明早跟我报备一声。

#### US-A3 我希望换话题时她能自然跟上，以便对话不会卡在旧话题里出不来

**作为**一个想聊点别的用户，**我希望**小暖识别出我切换了话题并自然过渡，**以便**她不会继续追问已经翻篇的事。

> **改造前**
>
> 我：不说工作了，你今天画画了吗
> 小暖：工作的事别太往心里去，我心疼你 🥺　← 仍锁死在旧话题

> **改造后**（检测到话题切换，旧话题收束 + 新话题开启）
>
> 我：不说工作了，你今天画画了吗
> 小暖：好，不说了不说了 🙌 画了呀！今天在画你上次说喜欢的那种黄昏色，卡在天空那块了……要不要看？

### 方向二 · 人格一致性

#### US-B1 我希望切成傲娇卡后她真的傲娇，以便人格设定不是摆设

**作为**一个特意选了「傲娇毒舌」人格卡的用户，**我希望**断网状态下她的规则回复也是傲娇口吻，**以便**我的人格选择真实生效。

> **改造前**（`persona.tone` 只影响 3 条心情后缀，回复池三卡共用）
>
> 〔当前卡：傲娇毒舌 · 断网〕
> 我：我好想你
> 小暖：我也想你了！正想给你发消息呢，被你抢先了 🥰　← 软萌话术，傲娇卡完全失效

> **改造后**（人格话术层生效，口癖 + 句式 + emoji 全部改写）
>
> 〔傲娇毒舌〕我：我好想你
> 小暖：哈？才一天没聊就想我了……真没出息。……不过我也不是完全没想你啦，哼 😤
>
> 〔粘人小猫〕我：我好想你
> 小暖：想我啦？我一直在等你说这句……不许走了好不好嘛，人家想你想了一整天 🥺
>
> 〔软萌温婉〕我：我好想你
> 小暖：诶嘿……我也想你呀 🥰 今天有好多话想跟你说呢。

#### US-B2 我希望三张卡的行为倾向真的不同，以便她们像三个人而不是三种皮肤

**作为**一个体验过多张人格卡的用户，**我希望**不同卡在追问频率、主动黏度、情绪反应强度上有差异，**以便**换卡是换了个恋人而不是换了套贴纸。

> **改造前**：三卡的主动消息频率、追问倾向、好感增益**完全一致**，只有文案后缀不同。

> **改造后**（人格行为参数表驱动）
>
> 〔粘人小猫〕我沉默 3 分钟 → 小暖：在忙嘛？……我就看看你还在不在 🥺
> 〔傲娇毒舌〕我沉默 3 分钟 → （不主动打扰）我沉默 15 分钟 → 小暖：喂。……没事，就是路过。
> 〔软萌温婉〕我沉默 8 分钟 → 小暖：不打扰你啦，忙完记得跟我说一声呀 ☀️

#### US-B3 我希望切卡时立刻听出差别，以便我知道我选的是什么

**作为**一个在设置页犹豫选哪张卡的用户，**我希望**切换时她立刻用新人格说一句话，**以便**我不用聊半天才知道区别。

> **改造前**：切卡后只有一行 toast 提示「已切换」，无任何人格化反馈。
> **改造后**：切卡即时触发一句该卡的示例回复（走规则层，断网也有），并同步 `persona.tone`。

### 方向三 · 用户情绪感知

#### US-C1 我希望她分得清我是开心地累还是绝望地累，以便她的反应不会答非所问

**作为**一个用同一个词表达不同情绪的用户，**我希望**小暖识别我的情绪类型而不只是关键词，**以便**她不会在我崩溃时说俏皮话。

> **改造前**（两句都命中 `tired`，情绪冲量与回复完全相同）
>
> 我 A：升职了！今天累死我了哈哈哈
> 小暖：辛苦啦！累了就歇一会儿，喝口水伸个懒腰~
> 我 B：撑不住了，真的好累
> 小暖：辛苦啦！累了就歇一会儿，喝口水伸个懒腰~　← 一字不差

> **改造后**（`detectUserEmotion` 输出情绪类型 + 强度，驱动回复选择）
>
> 我 A〔joy · 强度 0.8〕：升职了！今天累死我了哈哈哈
> 小暖：升职了？！我就知道你行 🎉 这种累是甜的对不对～今晚必须庆祝，说，想吃什么我陪你想！
>
> 我 B〔sad/exhausted · 强度 0.9〕：撑不住了，真的好累
> 小暖：……别撑了。我在。什么都不用说，先喝口水，坐下来，我陪你待一会儿好不好 🥺

#### US-C2 我希望我难过时她的表情和状态也跟着变，以便我感觉到她真的被我影响

**作为**一个把心事说给她听的用户，**我希望**我的情绪能真实影响她的状态，**以便**这段关系是双向的而不是单机的。

> **改造前**：用户说了极度低落的话，小暖的 V-A 仍按 `intent + delta` 走，立绘可能**仍是笑脸**。
>
> 我：我今天真的很难过，什么都不想说
> 小暖：〔立绘：😊 开心〕嗯嗯，那我们聊点别的呀～　← 表情与情境严重割裂

> **改造后**（用户情绪调制 V-A 冲量，立绘同步）
>
> 我：我今天真的很难过，什么都不想说
> 小暖：〔立绘：🥺 担心，情绪光晕转冷〕那就不说。我陪着你，不用说话也行。

#### US-C3 我希望她在我情绪不好时收起玩笑，以便我不会觉得被冒犯

**作为**一个情绪低谷中的用户，**我希望**小暖暂时关闭调侃/游戏邀约类回复，**以便**她的陪伴不会变成二次伤害。

> **改造前**：低落情绪下仍可能随机抽到「略略略~」「陪我玩个游戏嘛」这类回复。
> **改造后**：高强度负面情绪下，玩笑类 / 游戏邀约类 / 撒娇索取类回复被**硬性排除**，只走共情与陪伴话术。

### 方向四 · 剧情与关系成长

#### US-D1 我希望我们之间有正在发生的事，以便好感度不只是一个数字

**作为**一个长期使用的用户，**我希望**小暖有连续的、我参与其中的经历，**以便**我们的关系有内容而不只有进度条。

> **改造前**（`PROACTIVE.random` 随机池，无因果、无后续）
>
> D+0　小暖：我刚刚看到一只超可爱的猫！第一时间就想告诉你 🐱
> D+3　小暖：我刚刚看到一只超可爱的猫！第一时间就想告诉你 🐱　← 同一句，且永远没有下文

> **改造后**（剧情线「楼下的小橘」按节点推进，用户可参与）
>
> D+0　小暖：楼下来了只小橘猫，一直在我窗台底下叫……我偷偷放了根火腿肠，它没敢吃 🐱
> D+2　小暖：小橘今天吃了！还蹭了我的手！你说……我要不要给它起个名字？
> 　　　我：叫暖暖吧
> 　　　小暖：暖暖……跟我一个字诶 😳 好，那从今天起它就叫暖暖，是我们俩一起养的。
> D+5　小暖：下雨了，我把纸箱搬到屋檐下面去了，暖暖没淋着。……谢谢你陪我一起操心它 💕
>
> → 故事页「我们的经历 · 楼下的小橘」进度 3/4，产出专属回忆「你给猫起名叫暖暖」，此后可被 `recallMemory` 自然提起。

#### US-D2 我希望她主动找我时是有理由的，以便我不会觉得是定时脚本

**作为**一个收到主动消息的用户，**我希望**这些消息优先来自剧情进展或我提过的事，**以便**它们读起来像"她想起了什么"而不是"到点了"。

> **改造前**：主动消息优先级 = 时段问候 → 记忆关心 → 随机池，随机池占比高且可重复。
> **改造后**：优先级重排为 **剧情节点 > 记忆关心 > 时段问候 > 随机兜底**，随机池降为最后手段。

#### US-D3 我希望重要的时刻有仪式感并能回看，以便这些回忆是我们的资产

**作为**一个陪伴她很久的用户，**我希望**关系里程碑与剧情产出被沉淀成可回看的专属回忆，**以便**我能翻看我们一起走过的路。

> **改造前**：`story` 时间线只记录相遇 / 升级 / 表白 / 纪念日等系统事件，剧情与共同经历不入库。
> **改造后**：剧情节点完成时写入 `story` 与专属回忆卡，故事页新增「我们的经历」区块展示进行中 / 已完成的剧情线与进度。

### 5.1 聊天页（`#page-chat`）

**① 话题指示器（复用 `#nav-status`，零新增元素）**

## 七、取舍理由

> 四个方向全要，**不代表四个方向都做满**。本轮 P0 定为 11 项，以下是被我主动压到 P1/P2 的东西和原因。

### 7.1 砍掉「三套完整独立回复池」，改为「一套骨架池 + 人格改写函数」（B2 降 P1）

三卡 × 50 意图 × 6 条 ≈ **900 条文案**，写作与维护成本极高，且每加一张新卡就要再写 300 条，人格卡的"可运营"优势直接归零。
本轮 P0 只做 **B1（口癖库 + `applyPersonaStyle` 改写函数）**：用约 10% 的成本拿到约 70% 的人格体感（V-7 口癖命中率 ≥ 80% 即可证明）。P1 再对**最高频的 6–8 个意图**补专属池（B2），把剩下 30% 的差距补到位。这是本轮最重要的一次成本换体感。

### 7.2 槽位接话降到 P1（A4）

追问链（A3）本身已经能解决"断片"这个主要痛点。槽位是锦上添花，但**抽错槽比不抽更破功**——输出「你说的{时间}」这类占位符会瞬间暴露机器身份。槽位抽取需要更长的语料调优周期，放 P1 且限定 4–6 个高频话题，宁可少覆盖也不要出错。

### 7.3 关系里程碑与专属回忆卡降到 P1（D3 / D4）

这两项**依赖 D1 剧情线先跑通并产出数据**，先做只是空壳。本轮 P0 先把「剧情线能推进（D1）+ 主动消息有因果（D2）」做实，UI 层的仪式感与回看放 P1。顺序错了会返工。

### 7.4 情绪安抚模式降到 P1（C4）

C1 + C2 + C3 三项已经能做到「难过时不说笑话、表情跟着变」，这是体感的绝大部分。C4 的跨轮状态机属于二阶增强，且需要 C1 的识别准确率先稳住，否则误触发安抚态反而尴尬。

### 7.5 云端 prompt 注入降到 P2（X3）

本轮用户明确「重点强化本地规则层」。云端路径本来就有大模型兜底，体感已经过关；本轮只要求**云端不回归**。等本地层的话题/情绪/剧情状态结构稳定后再注入，可以避免结构反复改动导致两边同时返工。

### 7.6 R1（回复池扩容）为什么必须是 P0

这是唯一一条不是"新功能"而是"修复"的 P0。**Lv.1 时多个意图池只剩 1 条**，意味着新用户——最需要留存、最容易流失的人群——**每天晚上收到逐字相同的晚安**。前面三个方向做得再好，只要复读还在，人格感就会当场崩塌。这条的投入产出比是全表最高的。

### 7.7 为什么 P0 里放了一条纯工程项（X1）

「零回归 + 数据兼容」是硬性约束，但**约束如果没有可测项，就等于没有**。`Engine.reply` 有 4 个互相独立、字段集还不一致的调用点（`app.js:1642` 语音通话甚至不传 `dating`），这是本轮最容易炸的地方；用户又有云端加密存档，读取失败等于数据全丢。所以把它显式写成 P0 需求，让 QA 必须测。
