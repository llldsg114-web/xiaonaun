# PRD-v18 contingency 预算重谈与探针入网

## 1. 产品目标

**v18 一句话目标**：在 totalMax 276480 与 engineBase 245737 两条不可动红线之下，通过**纯模块侧配额重分配**把 `contingency.js` 从「仅余 19B」的临界态救出，同时补齐 v17 遗留的两项工程健全性缺口（零宽字符归一化盲区、探针未入 CI），全程不破体积四锁、不引入任何破墙泄漏。

**与 v17 承接**：

- v17 已完成路径 A 让渡（engineNetMax 2400→2800，moduleSumMax 28343→27943，totalMax 不动），四锁恒等式自洽、松弛 0、`over=[]`，QA 独立复核 PASS。
- v17 收口后进入**「打满即恰好」态**：三锁松弛为 0，天花板无兜底间隙。任何一侧超支直接击穿。
- v17 QA 风险登记 R-1（**高**）：`contingency.js` 5652/5671，余量 **19B**，再加一条语料即破锁 ②/④ —— 这是 v18 的第一顺位问题。
- v17 QA §7-D（低危）：`pnorm` 未清除零宽字符，`我是A\u200BI` 实测不被拦截。
- v17 QA §7-F（过程）：`npm test` glob 为 `test/*.test.js`，漏掉 8 个探针文件，直接导致 §7-A 变异探针崩溃潜伏至验收期才被发现。

**口径声明**：本 PRD 所有体积数字以 `Buffer.byteLength` 实测为准，已由产品侧 `wc -c` 独立复核一致（engine 248353 / memory 13333 / presence 3566 / texture 4366 / contingency 5652，total 275270）。

**边界声明**：v18 **不新增**面向用户的对话能力，是一轮预算与工程健全性收敛。配额精确终值由架构师高见远在 DESIGN-v18 裁定，本 PRD 只给选项、触发条件与算术草案。

## 4. 预算重谈（核心章节 · contingency）

### 4.1 实测基线（v17 终局 · 已 `wc -c` 复核）

| 项 | 实测 | 配额 | 闲置 | 备注 |
|---|---|---|---|---|
| `engine.js` | 248353 | 248537 | 184 | `engineNet` 2616 / 2800 |
| `memory.js` | 13333 | 13824 | **491** | 可让渡 |
| `presence.js` | 3566 | 3840 | **274** | 可让渡 |
| `texture.js` | 4366 | 4608 | **242** | 可让渡 |
| `contingency.js` | **5652** | **5671** | **19** | ⚠ 临界，受援方 |
| `moduleSum` | 26917 | 27943 | **1026** | = 491+274+242+19 ✓ |
| `total` | 275270 | 276480 | 1210 | = 1026 + 184 ✓ |

**四锁现状**（DESIGN-v17 §2.5 唯一自洽解）：
① `248537 = 245737 + 2800` ✓ ② `13824+3840+4608+5671 = 27943` ✓（严格等式）
③ `245737+2800+27943 = 276480 ≤ 276480` ✓（**松弛 0**）④ 无倒挂 ✓

**问题陈述**：模块侧总闲置 1026B 中，**98.1%（1007B）积压在 memory / presence / texture 三个不需要它的模块**，而唯一的功能扩展载体 `contingency.js` 只分到 19B。这不是「预算不够」，而是**预算错配** —— 因此 v18 的正解是重分配，不是抬天花板。

> ⚠ **可让渡额是动态量**：1007B 建立在三模块实测 13333/3566/4366 之上。若 v18 有任何改动落在这三个文件（如 P1-3、P2-3），可让渡额同步缩水，须在 T0 时点按当时实测**重算**后再冻结配额。

### 4.2 选项清单

| 选项 | 做法 | Δ红线 | V33 | 代价 | 评价 |
|---|---|---|---|---|---|
| **A · 模块侧重分配**（推荐） | memory/presence/texture 让渡闲置配额给 contingency，`moduleSumMax` **27943 不变** | 均不动 | **不变 248537** | 三让渡方缓冲变薄 | ✅ 首选 |
| **B · engine → 模块让渡** | 降 `engineNetMax`、等额抬 `moduleSumMax` | `totalMax` 不动，`engineBase` 不动 | **必须同步** | 挤占 engine 侧空间（P2-1 零宽字符还要吃 ~30B） | 备选，仅当 A 不足 |
| **C · 抬 `totalMax`** | 276480 → 更高，四锁重设 | **破 270KB 承诺** | 必须同步 | 改动面大、需全量回归、违背 v14 锁定 | 末选 |
| **D · 不加配额 · 砍语料** | 走 DESIGN-v17 §9-Q2 降级（每型 3→2 条） | 均不动 | 不变 | 牺牲功能 | 保功能优先于砍功能，仅兜底 |

**选项 A 详解（推荐）**：纯模块内部转移，`moduleSumMax` 恒为 27943 ⇒ 恒等式 ②③ 自动继续成立、松弛保持 0、`engineMax` 与 V33 不受影响、`totalMax` 与 `engineBase` 两条红线零触碰。**这是唯一一条不需要动任何跨层锁的路径**，回归面最小。上界 **1007B**（见 §4.4）。

**选项 B 详解（备选）**：`engineNet` 现余 184B，扣除 P2-1 零宽字符加固 ~30B 后约余 154B。示例自洽解：`engineNetMax 2800→2700`（让渡 100B），`engineMax 248537→248437`，`moduleSumMax 27943→28043`，校验 ③ `245737+2700+28043 = 276480` ✓。**代价是 V33 三处必须同步更新（P0-3）**，且 engine 侧缓冲压到 ~84B，`:1307` 后续任何扩展都将无空间。仅在 A 的 1007B 上界不足时启用。

**选项 C / D**：C 直接破 v14 锁定的 270KB 承诺，非到硬顶击穿不用；D 与产品路线冲突，仅作最终兜底。

### 4.4 推荐路径与算术草案

**推荐：选项 A · 纯模块侧重分配**，理由 —— 不抬 `engineNetMax`、不抬 `totalMax`、不动 `engineBase`、V33 保持 248537、四锁恒等式与松弛 0 全部自动维持，是回归面最小的一条路。

**可让渡上界推导**（全部为实测差值，可复算）：

```
memory.js     13824 − 13333 = 491
presence.js    3840 −  3566 = 274
texture.js     4608 −  4366 = 242
                        小计 = 1007  ← 可让渡上界（contingency 自身 19B 不计）
contingency 自身闲置                = 19
                  模块侧闲置合计     = 1026  ✓ = 27943 − 26917
```

**三档草案**（Σ 恒 = 27943，`moduleSumMax` 不变）：

| 档 | 让渡方保留缓冲 | memory | presence | texture | **contingency** | 让渡合计 | Σ 校验 | contingency 净余 |
|---|---|---|---|---|---|---|---|---|
| **A1 极限** | 0B | 13333 | 3566 | 4366 | **6678** | 1007 | 27943 ✓ | **1026** |
| **A2 推荐** | 32B/模块 | 13365 | 3598 | 4398 | **6582** | 911 | 27943 ✓ | **930** |
| **A3 保守** | 64B/模块 | 13397 | 3630 | 4430 | **6486** | 815 | 27943 ✓ | **834** |

Σ 逐档验算：
`13333+3566+4366+6678 = 27943` ✓　`13365+3598+4398+6582 = 27943` ✓　`13397+3630+4430+6486 = 27943` ✓

**产品侧倾向 A2（contingency 5671 → ~6582，净余 930B）**：
- 恰好覆盖 v17 R-S2 同量级（~900B）的一批新增语料，且仍留余；
- 三个让渡方各保 32B 缓冲，避免 A1「缓冲 0，任何一个字节的改动都破锁 ④」的脆性；
- 若架构师判定 v18 落 contingency 的量更小，可直接采 **A3**（更安全）；若确认语料量逼近 1000B，则采 **A1** 并**同时冻结三让渡方源码**（禁止本轮对其做任何字节改动）。

**四锁复核（以 A2 为例）**：
① `248537 = 245737 + 2800` ✓（未触碰）
② `13365 + 3598 + 4398 + 6582 = 27943 = moduleSumMax` ✓（严格等式）
③ `245737 + 2800 + 27943 = 276480 ≤ 276480` ✓（松弛仍为 0）
④ `13365>13333` / `3598>3566` / `4398>4366` / `6582>5652` ✓（T0 时点无倒挂）
⑦ `V33 = engineMax = 248537` ✓（**不变**，因 `engineNetMax` 未动）

> 📌 **精确终值由架构师高见远在 DESIGN-v18 裁定。** 本节只提供选项、触发条件与可复算的算术草案；产品侧不锁定具体数字，但要求终值必须满足：Σ 严格 = 27943、④ 无倒挂（T0/T4 双时点）、且在文档中给出与本表同格式的验算。
>
> 📌 **若未来确需 engine 侧扩张，另立预算项**，不与本轮 contingency 重分配混谈 —— 避免 v17「一次让渡同时服务多个诉求、结果双方都只剩薄缓冲」的重演。

  - **黑名单**（推荐，造价小）：`[\u200B-\u200D\uFEFF]` 约 +30B，覆盖 ZWS/ZWNJ/ZWJ/BOM 四类，与 QA §7-D 建议一致；
  - **扩展黑名单**：追加 U+200E/200F（LRM/RLM）、U+2060（WJ）、U+180E，覆盖更广但造价上升；
  - **白名单**（只保留 CJK + ASCII + 常用标点）：最彻底，但**误杀风险高**，且与 G2「一票否决优先于拦截率」裁定冲突，产品侧**不建议**。
  另需确认：ZWJ（U+200D）被 emoji 序列合法使用，直接剥离是否影响 emoji 渲染路径？—— 但 `pnorm` 仅用于**护栏判定副本**、不改写输出文本，初判无影响，请架构师确认。

- **Q3（P1-2 落地形态）**：**`test:probe` 是否进 pre-commit？**
  - 探针（尤其六维 1,034,880 与异构 860,160）运行耗时可能达分钟级，进 pre-commit 会显著拖慢提交；
  - 产品侧倾向：**pre-commit 只跑快探针子集**（如 `qa-v17-independent-size.js` 体积四锁、`qa-probe-mutation.js` 变异非空性），**全量探针进 CI + 交付自检清单**；
  - 需确认是否拆 `test:probe`（全量）与 `test:probe:fast`（快子集）两个 script。

- **Q4（口径）**：**P2-3 `scanSizes().over` 补全**是否本轮做？补全后 `over=[]` 才真正等价于「四锁全绿」，但会改动 `wiring-scan.js` 逻辑而非仅常量表，需评估是否与 P1-1 同 PR。

- **Q5（流程）**：v18 是否沿用 v17 的 **T0 配额先落、源码 0 diff** 双时点节奏？若沿用，则 §4.3-T4 的「按 T0 实测重算」必须在 T0 之前完成，请架构师在 DESIGN-v18 明确时序。
