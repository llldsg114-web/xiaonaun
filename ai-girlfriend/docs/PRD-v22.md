## 0. 前提校正（必读 · 五处 ghost）

v21 交付总结移交给 v22 的三个"前相传项"，其中**三项的前提描述与仓库实况不符**。若照单全收起草，v22 会从第一行开始自相矛盾。逐条列明：

### G-1 ✗「engine.js 零字节增量是常设铁律」—— 不成立

- **实况**：`diff=0` 硬闸（`T0_BYTES`，`qa-v19-quota-gate.js:88`）**只覆盖 4 个数据模块**（memory / presence / texture / contingency）。`engine.js` 不在其中。
- engine.js 受的约束是 `engineNet ≤ engineNetMax`，当前 **2658 / 2700，余 42B**（门禁 E 段实测输出）。
- 四锁 ①②③④ 中**没有任何一条**要求 engine.js Δ=0。
- `git log -- engine.js` 显示 engine.js 在 v13/v14/v15/v16/v17/v18 六个版本中均有改动；"零预算"是 **v19–v21 连续三版的自我约束选择**，不是 frozen truth。
- **影响**：若按字面理解为铁律，则 P0-2（H13 正则扩展）**永远不可落地**，PRD 将自我否定。
- **v22 口径**：engine.js 可动，但**仅限授权解冻点**（`:1307` / `:1310` / `:1322`），且须满足 `engineNet ≤ engineNetMax` 与 H13 0% 双约束。**"零预算"降级为默认偏好，不是禁令。**

### G-2 ✗「H13 修复须先解决配额才能落地」—— 半不成立

- QA-v21 §10 F-2 估算修复成本 `+18~24B`。**实测该估算偏低。**
- 实测最省的**零误伤**方案为 **+41B**（见 §0/G-5 对照表），落在现有 42B 余量内 → **不重谈配额也能落地**。
- 但落地后 `engineNet = 2699 / 2700`，**余 1B**，engine 侧缓冲归零。
- **v22 口径**：重谈配额的理由**不是"落不下"，而是"落下后无缓冲"**。P0-1 与 P0-2 是"强烈建议同轮"而非"硬阻塞"关系。此区别影响排期灵活度，不可含混。

### G-3 ✗「第 5 语料型 routing 受 engine 零预算约束」—— 不成立

- `sfType()` 定义在 **`contingency.js:33`**，不在 engine.js。
- 启用路由**完全不触达 engine.js**，不受零预算、不受 H13 约束。
- 成本落在 contingency 配额内（余 56B，严格 `>` 下可用 55B）。
- **影响**：三项议题中，routing 是**最便宜、风险最低**的一项，不应被"配额紧张"叙事连带绑架、继续拖延。

### G-4 ✗「V33 三针」—— 严重低估同步面

实测字面量分布（`grep -rln`）：

| 字面量 | 含义 | 分布文件数 |

| `248437` | engineMax / V33 | **7** |

| `13365` / `3598` | memory / presence 配额 | 各 **5** |

- v21 沿用的"三针"清单（`wiring-scan.js:373` / `qa-v13-t2t4-fix.js:117` / `qa-v16-size-probe.js`）**已过时**。DESIGN-v21 §1.2 亦已提示"勿只改 3 处"。
- **v22 口径**：任何配额变更必须走**全量扫描同步**（`grep -rn` 旧值，计数归零），**禁止**按"三针"清单办事。

#### **P0-3 · 第 5 语料型 routing 裁决**

**描述**
消除 PRD-v21 P0-6/AC-7（要求"可路由命中、非死代码"）与 DESIGN-v21 T03（定为纯数据增强、`sfType()` 不路由）之间的长期矛盾。QA 已就现状增设 AC-RS2-9 锁死"选型层暂不可达"。

**PM 裁决建议：✅ 启用路由（方案一），否决"正式关闭为纯数据资产"**

理由：
1. **产品缺口是真实的**：现有四型中 `boundary` 负责"设界/冲突"，**无任何一型负责"冲突后修复"**。AI 女友的核心情感闭环是"能吵架、也能和好"，缺 repair 等于关系只能单向劣化。
2. **成本极低且不触达 engine.js**：`sfType()` 在 `contingency.js:33`，不受零预算/H13 约束。经测算，改为嵌套三元 `S.security<.5?p<0?"boundary":"repair":…` 仅 **+8B**（原片段 30B → 38B），落在 contingency 余 56B 内，宽裕。
3. **关闭 = 承认 356B 死重**：6 条 repair 语料已随包下发给所有用户，永不可达即纯字节浪费；在"余量以个位数计"的治理语境下自相矛盾。
4. **是 DESIGN 偏离 PRD，不是 PRD 定错**：v21 DESIGN 单方面降级了 PRD 已批准的验收标准。正确的修法是补齐实现，而非追认降级。

**AC**
- AC-3.1 `sfType()` 在特定情境下**确实返回** `repair`，可由采样证明（非死代码）
- AC-3.2 **五型均仍可达**：`stable` / `expand` / `challenge` / `boundary` / `repair` 逐型给出可达性证据 —— **不得出现"修好 repair 却压死 challenge"的遮蔽事故**（参考 AC-RS2-4b 已记录的 expand 遮蔽先例）
- AC-3.3 QA 侧 **AC-RS2-9 须同步改写**：现断言"永不返回 repair"，启用路由后该断言必然转红，须改为"repair 可达 + 五型互不遮蔽"。**此为预期内转红，不得当作回归事故绕过**
- AC-3.4 `contingency.js` 增量落在配额内：落地后实测 < 6682（严格 `>`），预计 6634 左右，余 ~48B
- AC-3.5 `T0_BYTES["contingency.js"]` 6626 → 新实测值，走三件套，**且必须在代码落地之后独立发生**（先红后绿）
- AC-3.6 触发语义须**符合直觉**：repair 应出现在"刚发生过冲突/设界、当前语气回暖"的情境，不得在冷启动或平静对话中冒出道歉

**关联锁/约束**：锁④（contingency）、锁⑧、`T0_BYTES` 三件套
**待架构师定夺**：repair 的具体触发条件与四型的遮蔽边界（PRD 只约束"可达且不遮蔽"，不指定判据）

```
  openness>=.5 && len(u)>19     → "expand"
  否则                            → "stable"
```

**设想**（PM 级语义，判据由架构师定）：

```
sfType(s,c,u) →
  security<.5 ┬ p<0   → "boundary"     ← 冲突/设界当下
              └ p>=0  → "repair"       ← ★新增：刚设过界、气氛回暖
  independence>=.55 && v>=5 && p>=0 → "challenge"
  openness>=.5 && len(u)>19         → "expand"
  否则                                → "stable"
```

- **语义**：`security` 低 = 关系刚受过冲击；`p` 由负转正 = 用户语气缓和 → 正是"和好"窗口。
- **形态**：嵌套三元复用已有 `security<.5` 判断，成本约 **+8B**。
- **handler**：`selfOf(tier, type, r)` **无需改动** —— 它已按 `SFT[y]` 取表，`y="repair"` 天然可取到 6 条语料（AC-RS2-9 现有断言已证明 `selfOf("open","repair",…)` 取样正常）。**故本项只改选择器，不改渲染链路。**
- ⚠ **遮蔽风险（须架构师评估）**：`security<.5 && p>=0` 分支现状会落到 challenge/expand/stable。改判为 repair 会**抢走部分 challenge 命中**。AC-3.2 要求五型均可达，架构师须据此收紧判据（例如叠加"近期发生过 boundary"的状态位）。
