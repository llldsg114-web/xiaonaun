## §5 门禁红→绿全过程取证（本轮最关键的一组）

流程约束的意义：若把"改语料"和"改基线"合进一个任务，门禁**从头到尾不会红过一次**，
本轮门禁的作用就等于零。故 T03 被刻意拆为独立任务。实测轨迹：

```
【T01 交付后】语料已落盘，基线未同步 —— 设计预期的红
  FAIL contingency.js 字节 === 基线  → 实测 6270 / 基线 5652 / Δ+618
  === 配额门禁总判定: FAIL ===   exit 1

【T03 交付后】履行三件套，基线同步至 6270
  ok   contingency.js 字节 === 基线  → 实测 6270 / 基线 6270 / Δ+0
  ok   ④ 逐模块配额 > 基线            → … / 6582>6270
  === 配额门禁总判定: PASS ===   exit 0
```

**三件套履行记录**（DESIGN-v19 §4.4 / DESIGN-v20 §5.8）：
① `SIZE_BUDGET` 调整 → **经审视，判定无需变更**（Δ 落在既有配额内）——

## §7 ★ 929B 安全上限（写给 v21，请先读这一节）

```
配额 SIZE_BUDGET["contingency.js"]          = 6582
门禁锁④允许的最大实测字节 = 配额 − 1        = 6581
v19 收口锚点（T0 基线起点）                  = 5652
────────────────────────────────────────────────────
★ 安全 Δ 上限 = 6581 − 5652 = 929 B  （不是 930！）
本轮实际用掉 618 B，余 311 B。
```

成因：门禁锁④用严格 `>`，业务锁用 `≤`，**两者对同一个天花板的答案相差恰好 1 个字节**。
Δ=930 时门禁判 `6582 > 6582` = false 转红，而业务测试判 `6582 <= 6582` = true **仍绿** ——
**业务侧对越界毫无察觉**。这不是缺陷，是两条锁语义不同的正确外显（详见 DESIGN-v20 §1.3）。

**排预算铁律**：后续版本一律按 **929** 排，不按 930 排。
若确需用满第 930 个字节，那不叫"用满余量"，那叫**配额重谈**，必须走三件套。
