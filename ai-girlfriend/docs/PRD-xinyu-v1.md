## 0. 前提复核（必读 · 主理人 recon 之外新发现的 3 个阻断点）

主理人给出的 A–E 侦察结论我逐条回读了源码核验。**A/B/D/E 全部属实**，C 节口径不完整。另有两处会让「改名生效」或「测试转绿」直接失败的点，recon 未覆盖。逐条列明——**这三条是架构师必须吃进方案的，不是可选优化**。

### 补正 R-1 ✗「移除 `<title>` 的 `data-xn="title"` 就够了」—— 不成立（P0 阻断）

- **实况**：`app.js:3793` 有一行**独立于 data-xn 循环**的直写：
  ```
  if (typeof document !== "undefined") document.title = `${ch.name} · 你的 AI ${role}`;
  ```
- `ch.name` = 角色名「小暖」。即使把 `index.html:9` 的 `data-xn="title"` 摘掉（那只挡住 `:3795` 的 textContent 循环），`applyCharIdentity()` 一执行，浏览器标签页标题**仍会被覆写回「小暖 · 你的 AI 女友」**。
- **结论**：改名要真正生效，`index.html:9` 与 `app.js:3793` **必须成对处理**，缺一即验收失败。详见 §2 映射表第 3、4 行。

### 补正 R-2 ✗「sw 只需把 `cacheVersion` 改 v26」—— 不完整（P0 阻断）

- `test/qa-v21-sw-guard.js` 的 **C 段**会对 `sw.js` ASSETS 的**每个成员现算 sha256**，与 `test/sw-assets-manifest.json` 的 `assets` 块逐条比对，不一致即转红（注释原文：「清单是否忘了重算」）。
- 本轮改动落在 ASSETS 内的成员有 **6 个**：`/index.html`、`/`（与 index.html 同源同哈希）、`/style.css`、`/app.js`、`/manifest.json`、`/icon-192.png`、`/icon-512.png`。
- **结论**：除 `cacheVersion: xiaonuan-v25 → xiaonuan-v26` 外，**`assets` 块内这些条目的 sha256 必须全部重算**。只改版本号 = guard C 段红。
- `released` 块**逐字不动**（C-2 纪律，主理人已明示，此处复述为红线）。

### 补正 R-3 ✗「缓存键可以顺势改成 `xinyu-v26`」—— 严禁（P0 阻断）

- `qa-v21-sw-guard.js:243` 的版本号解析器是**硬编码正则**：`/^xiaonuan-v(\d+)$/`。
- 一旦把前缀改成 `xinyu-`，F1（命名可比较）与 F2（单调不回退）立刻 NaN 转红，且 `released` 锚点 `xiaonuan-v23` 无法与之比较，反逃逸参照系直接失效。
- **结论**：`xiaonuan-` 前缀是**技术标识**，与存储 key `xiaonuan_save_v1`、npm `name: "xiaonuan"` 同类，**不在产品改名范围内**。只升数字：`xiaonuan-v25 → xiaonuan-v26`。

### 复核确认（recon 属实，无需调整）

| 侦察项 | 复核结论 |
|---|---|
| A · `data-xn="appname"` 不在动态循环内 | ✅ 属实。全量 grep `app.js` 只有 `name`/`title`/`-prefix`/`-ph`/`-title`/`-cardsub`/`-voice`/`-tts`/`-cloud` 九类，**无 `appname` 分支**，是静态 meta |

## 1. 产品目标与改名语义

**一句话定义**：**「心屿」是这座岛（应用/产品），「小暖」是岛上等你的那个人（AI 角色）**。用户打开手机主屏点的是「心屿」，进去之后叫她的名字仍然是「小暖」。

| 层 | 名称 | 含义 | 出现位置 | 本轮动作 |
|---|---|---|---|---|
| 产品层 | **心屿**（Xinyu） | 应用/容器/品牌 | 主屏图标名、标签页标题、iOS 添加到主屏名、设置页页脚版本行 | **改**（5 处，见 §2） |
| 角色层 | **小暖**（xiaonuan） | AI 女友本人（男版为「阿言」） | 聊天页 nav、她页大标题、通话浮层、tabbar、splash 名、全部 UI 文案、推送发信人名 | **一个字都不动** |
| 技术层 | `xiaonuan` | 内部标识符 | 存储 key、sw 缓存键前缀、npm name、`from: "xiaonuan"` 推送字段 | **一个字都不动** |

**产品目标（3 条，正交）**

| # | 目标 | 可度量口径 |
|---|---|---|
| G1 | 建立「心屿」品牌外壳，且**零成本于角色沉浸感** | 产品级 5 处表面全部显示「心屿」；角色级表面「小暖」出现次数与改前**逐字相等** |
| G2 | 首屏识别度：动漫头像图标取代现占位图标 | 三尺寸图标（192/512/apple-touch）全部替换且 manifest 可解析、PWA 可安装 |
| G3 | 设置页从「13 张长条平铺」变为「可检索的分组面板」 | 首屏可视卡片数 13 → ≤ 6（分组头）；任一设置项 ≤ 2 步（搜索 or 展开）可达 |

**User Stories**

| # | 故事 |
|---|---|
| US-1 | 作为用户，我把 App 装到主屏后看到的是「心屿」和一个动漫头像，**这样它看起来像一个正经产品**而不是一个 demo |
| US-2 | 作为用户，我进入 App 后她依然叫「小暖」、依然是那个人，**这样改名不会让我觉得"我的女友被换掉了"** |
| US-3 | 作为用户，我去设置页找「云同步」时不用滚 13 屏，**这样我能在 5 秒内改完一个配置** |
| US-4 | 作为用户，我记不住某个开关叫什么，可以直接搜「推送」「模型」，**这样我不必逐张卡片扫读** |
| US-5 | 作为老用户，更新后打开书签直接是新版（不用清缓存、不用重装），**这样我不会看到新旧混装的界面** |

## 3. 图标方案

### 3.1 现状与产出物

| 项 | 值 |
|---|---|
| 源文件 | `ai-girlfriend/icon-xinyu.svg`（2207 B，512×512，粉→蓝渐变背景 / 爱心发夹 `#ff5b8a` / 正面萌系少女）—— **手绘占位**，非 AI 生图 |
| 成因 | 沙箱网络墙：pypi.org / github TLS 均被封，AI 生图链路不可用 |
| 可行性 | ✅ **栅格化不依赖外网**：本机已有 `/usr/bin/convert`（ImageMagick）与 Python `PIL` |

### 3.2 三尺寸产出（覆盖同名文件，路径不变）

| 目标文件 | 尺寸 | 被谁引用 | 在 sw ASSETS 内？ | 需重算 sha256？ |
|---|---|---|---|---|
| `icon-192.png` | 192×192 | `manifest.json:13`（`purpose: any`） | ✅ 是 | ✅ 是 |
| `icon-512.png` | 512×512 | `manifest.json:14`（`any`）＋ `:15`（`maskable`，**同一文件双 purpose**） | ✅ 是 | ✅ 是 |
| `apple-touch-icon.png` | 180×180（iOS 惯例） | `index.html:11` `<link rel="apple-touch-icon">` | ❌ 否 | ❌ 否 |

**要求**

- R-I1（P0）：三文件均为**覆盖写入同名路径**，不新增文件、不改 `manifest.json` 的 `icons` 数组结构、不改 `sw.js` ASSETS。
- R-I2（P0）：`icon-512.png` 同时充当 `maskable`，故主体（少女头像）必须落在**中心 80% 安全区**内，四周留白，避免 Android 圆形/水滴裁切切到脸。
- R-I3（P1）：背景**不透明**（渐变已铺满），避免 iOS 把透明区渲染成黑色。
- R-I4（P1）：栅格化后**人工目检**——ImageMagick 内置 MSVG 渲染器对渐变/曲线的还原度弱于 rsvg，若出现渐变断层、路径错位、锯齿，退回 PIL 直绘或等待真图。**目检不通过不得合入**。
- R-I5（P2）：主题色 `#ff7b9c`（`manifest.json:11` / `index.html:6`）与图标粉色系保持协调，本轮**不改主题色**。

### 3.3 真图后路（明确写给未来的自己）

占位图不是终点。满足以下**任一**条件时，替换动作是「覆盖三个 PNG + 升缓存键 + 重算三条 sha256」，**不涉及任何代码改动**：

| 触发条件 | 操作 |
|---|---|
| 环境放行 pypi/github（AI 生图链路恢复） | 生成 512 母图 → 派生三尺寸 → 覆盖 → 升 `xiaonuan-v27` → 重算 `icon-192/512` 指纹 |
| 用户直接提供 PNG/PSD 真图 | 同上，跳过生图步骤 |

> 因为**路径与引用全部不变**，图标升级永远是一次「纯资产替换」，架构层无需为此预留任何扩展点。

## 8. 待确认问题（3 条 · 均附推荐答案，不阻断动工）

### Q1 · splash 启动页是否改为展示产品名「心屿」？

- **背景**：`index.html:20` splash-name（`data-xn="name"`）运行时显示「小暖」，`:21` splash-sub（`data-xn="title"`）显示「小暖 · 你的 AI 女友」。主理人已决策**保留小暖**。
- **我的复核结论：同意主理人决策，保留「小暖」。** 理由三条：
  1. 启动页是**进入岛屿之后**看到的第一屏，此时用户已经点过主屏那个写着「心屿」的图标——品牌名在**图标那一步已经交付**，splash 再喊一次品牌名反而把「见到她」的情绪打断；
  2. splash-name 挂着 `data-xn="name"`，男版会显示「阿言」。若改成产品名就必须摘属性并硬编码，**男女双版的一致性反而更难维护**；
  3. 若日后想在 splash 体现品牌，成本更低的做法是加一行**极小号的副标题**「心屿出品」而非改主标题——这是 P2 增量，不必现在做。
- **推荐**：**保持现状不动**。若主理人坚持要体现品牌，选 P2 方案（splash 底部加小字），我可另开条目。

### Q2 · 图标先上占位 SVG 栅格图，还是等真图？

- **背景**：`icon-xinyu.svg` 是手绘占位，AI 生图被网络墙阻断；但本机 ImageMagick/PIL 可离线栅格化。
- **推荐：先上占位图，本轮闭环。** 理由：① 图标替换是**纯资产覆盖**，路径/引用/清单结构全不变，真图到位后重跑同样流程即可，**没有任何返工成本**；② 若为等真图而拖延，本轮的改名 + 设置页重构就要单独升一次缓存键，真图来了再升一次——**平白多一次 C0-b 操作 = 多一次犯错机会**。合并成一次 v26 更安全。
- **前置条件**：R-I4 人工目检必须通过（渐变断层/路径错位则退回 PIL 直绘）。目检不过就退化为「本轮不动图标」，改名与设置页照常发。

### Q3 · 设置页折叠态是否本轮就做持久化（M-10）？

- **背景**：主理人口径为「折叠态记忆可选」。
- **推荐：本轮**不做**，列 P2。** 理由：① 它需要新增一个 localStorage key，而本轮的核心纪律是「呈现层重构、存储层零改动」（INV-2）——引入新 key 会让 AC-15 的「存储零改动」判据从**布尔判定**退化成**需要逐项解释的判定**，削弱验收锋利度；② 收益有限：默认展开前两组已覆盖高频场景，且有搜索兜底；③ 若要做，建议下一版与「设置页偏好」一并设计一个统一的 UI 偏好 key，而不是本轮临时塞一个。
